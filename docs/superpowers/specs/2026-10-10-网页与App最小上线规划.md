# 网页与 App 最小上线规划

> 日期：2026-10-10（同日补充角色与动态路由；技术选型结论见第 9 节，仅作后续参考）
> 状态：待确认后按阶段实现
> 范围：网页（`ai-java-front`）与 HBuilderX App（`ai-app`）共用现有后端和同一个 MySQL 库 `ai_java`。首版让普通用户能注册并完成一次真实问答，让管理员在网页上管理用户、角色和菜单。菜单与路由由数据库下发，不在前端写死。风格蒸馏、提示词工坊、知识库成员共享、MCP 对外开放不进入首版。

## 1. 上线目标

普通用户在网页或 App 上可以独立完成：

1. 注册账号并登录。注册账号的角色固定为「用户」，不能自己选成管理员。
2. 创建自己的知识库。
3. 上传 PDF / Word / Markdown / TXT（单文件不超过 20MB）。
4. 看到文档处理完成或失败原因。
5. 针对该知识库发起多轮问答，并看到引用来源。
6. 退出登录后，旧的 Refresh Token 不能再换登录态。

管理员在网页上可以：

1. 用单独的管理员账号登录。
2. 只看到管理菜单：用户、角色、菜单、审计日志。
3. 查看用户、封禁或解封、把用户在「用户 / 管理员」两个角色之间调整。
4. 给角色勾选可见菜单。保存后，该角色下次进入系统时菜单和路由跟着变。
5. 查看审计日志。

管理员不读取别人的知识库、文档和会话。封禁、改角色、改菜单属于账号与权限管理，不属于查看用户私有内容。

两端调用同一套 `/api`。谁能看见哪个页面，由当前用户的角色决定；谁能调用哪个接口，由后端按同一套权限校验。前端隐藏菜单不算权限。

## 2. 首版不做

| 能力 | 处理方式 |
| --- | --- |
| 回答风格 / 数据集 / 评测 | 页面文件可留在工程里，首版不配给任何角色，菜单里不出现 |
| 提示词模板编辑 | 首版使用系统默认模板，不配菜单 |
| 仪表盘 Token 图表 | 不配菜单，不影响问答 |
| 知识库成员、共享 | 后补。数据范围仍是「创建者本人」 |
| 一个用户多个角色 | 后补。首版一个用户只有一个角色 |
| 按钮级权限（页面里某个按钮单独授权） | 后补。首版做到菜单可见性和接口权限 |
| MCP（`/api/mcp`） | 首版关闭。现有全局 Token 能检索全部用户的知识库 |
| 混合检索、重排序、向量重建 | 后补。失败文档仍按现有规则删除后重传 |
| App 上的管理后台 | 后补。管理页面只做网页。App 只呈现该角色被授权、且 App 已实现的页面 |
| iOS 上架 | 首版用 Android 调试基座验证，同一套 uni-app 稍后补 iOS 证书 |

## 3. 现状

后端主循环已经可用：注册登录（BCrypt、Access Token 2 小时、Refresh Token 7 天、连续失败锁定 30 分钟）、知识库与文档按 `userId` 隔离、异步摄取、SSE 流式问答、引用、审计日志。

账号只有 `user.status`，没有角色。`user` 表在库 `ai_java` 里。接口只有 `@RequireLogin`，登录之后不区分用户和管理员。

网页路由写死在 `ai-java-front/src/router/index.ts` 和 `router/ai.ts`，侧栏写死在 `AppSider.vue`。登录后的人都会看到仪表盘、知识库、提示词、回答风格、智能问答。直接输入地址也能打开这些页面。

`ai-app` 是 HBuilderX 生成的 uni-app Vue 3 空白工程，只有默认首页。uni-app 的页面必须在 `pages.json` 里于打包前声明，运行时不能像 Vue Router 那样 `addRoute`。App 的「动态」体现在：首页和菜单按接口结果生成，未授权页面不给入口，页面打开时再向后端确认一次。

上线前数据安全还过不了这些点：

- `application-prod.yml` 中数据库密码、JWT 密钥、模型 API Key 有明文或默认值。密钥一旦进过仓库，就要在云厂商侧作废并更换，不能只改文件。
- CORS 为 `allowedOriginPatterns("*")` 且允许携带凭证。
- 登录和刷新 Token 不检查账号状态。封禁用户仍可登录。
- 没有退出登录。Refresh Token 在过期前一直有效。
- Knife4j 在生产配置中开启。
- 上传文件在本机 `./uploads`。下载和删除必须只走「当前用户 + 文档 ID」，不能接受客户端传入的文件路径。
- App 模板 `manifest.json` 声明了相机、读日志、电话状态等权限。首版只保留网络访问。

## 4. 角色与动态路由

新表和 `user.role_id` 都建在现有库 `ai_java`，不新建库。脚本放在 `docs/sql/`，和现有 `ai_java.sql` 一起维护。

只建角色表无法实现动态路由：角色只说明「这个人是谁」，菜单路径、组件名、排序、归哪个角色，都要有地方存。首版用三张新表，用户表加一列。

### 4.1 表

`role` 角色。

| 列 | 说明 |
| --- | --- |
| id | 主键 |
| code | 唯一编码，首版只有 `USER`、`ADMIN` |
| name | 显示名：用户、管理员 |
| status | 1 启用，0 停用。停用后该角色不能登录 |
| remark | 备注 |
| create_time / update_time | 审计时间 |

内置两行不允许删除，不允许改 `code`。可以改名称和备注。

`menu` 菜单与路由资源。前端侧栏和动态路由都读这张表。

| 列 | 说明 |
| --- | --- |
| id | 主键 |
| parent_id | 上级，0 为根 |
| name | 菜单名，如「知识库」 |
| path | 路由路径，如 `/kb`、`/kb/:id`。目录可空 |
| component | 组件键，不是磁盘路径。例如 `kb/KnowledgeBaseView` |
| icon | 图标名，前后端约定一组现有图标 |
| sort | 同级排序 |
| menu_type | `CATALOG` 目录、`MENU` 页面、`BUTTON` 权限点（首版可先不配按钮） |
| permission | 接口权限码，如 `kb:view`、`user:ban`。目录可空 |
| visible | 是否出现在菜单。详情页可以为 0，但仍注册路由 |
| client | `WEB`、`APP`、`ALL`。管理菜单标 `WEB` |
| status | 1 启用，0 停用 |

`role_menu` 角色拥有哪些菜单。联合主键 `(role_id, menu_id)`。

`user` 增加 `role_id`，非空，指向 `role.id`。已有用户回填为 `USER`。一个用户一个角色。

### 4.2 初始数据

| 角色 | 菜单 |
| --- | --- |
| USER | 知识库、知识库文档（隐藏路由）、智能问答。`client` 为 `ALL` |
| ADMIN | 用户管理、角色管理、菜单管理、审计日志。`client` 为 `WEB`。不包含他人的知识库数据 |

注册写入 `role_id = USER`。第一个管理员用初始化脚本创建，密码来自环境变量，不把可用密码写进仓库。公开注册接口不接受角色字段；请求体里若带 `roleId`，忽略它。

提示词、回答风格、仪表盘先不插入菜单，或插入后不挂到任何角色。以后要开放，就在菜单管理里挂上，并保证组件键已经在前端白名单中。

### 4.3 登录后怎么发路由

1. 登录、刷新、当前用户接口的用户信息带上 `roleId`、`roleCode`、`roleName`。
2. 新增 `GET /menu/nav`。按当前用户的 `role_id` 查出启用菜单，组树返回。查询参数 `client=web|app`：`ALL` 始终返回，另外只返回对应端。
3. 网页只在代码里保留静态路由：`/login`、`/register`、布局壳、403、404。`router/ai.ts` 里的业务路由表和 `AppSider.vue` 里的写死菜单删除。
4. 登录成功或刷新页面时，先请求 `/menu/nav?client=web`，再 `addRoute` 到布局下。侧栏用同一份树渲染，不再维护第二份路径表。
5. 组件用白名单装载。后端只返回组件键，前端用键找到已存在的 `() => import("...")`。键不在白名单中的菜单丢弃并打日志，不根据接口字符串拼接路径去加载文件。这样菜单可以动态增删，同时避免接口内容被用来加载任意模块。
6. 守卫：没有 Token 去登录；已登录但目标路由不在本次下发结果里，打开 403。刷新整页时要等菜单加载完再放行，避免动态路由还没注册就被判成 404。
7. 改角色或改菜单后，该用户当前 Access Token 仍可能有效。后端每个业务请求按数据库里的角色和 `permission` 校验，不相信 Token 里缓存的角色，也不相信前端是否显示了菜单。角色被改或被停用后，下一次请求即生效。

App 拉取 `GET /menu/nav?client=app` 生成首页入口。`pages.json` 仍要列出已实现的页面，这是 uni-app 的打包限制。未出现在导航结果里的页面不展示入口；页面 `onShow` 时若权限不符，退回首页。管理菜单是 `WEB`，App 导航里不会出现。管理员若登录 App，看到的是空业务入口和一句说明：账号管理请使用网页。

### 4.4 接口权限

新增 `@RequirePermission("kb:view")` 一类注解，和 `@RequireLogin` 叠用。拦截器确认登录和账号 status = 1 之后，再查该用户角色是否拥有这个权限码。没有就返回 403。

首版权限码与菜单对应：

| 权限码 | 谁有 | 保护的接口 |
| --- | --- | --- |
| `kb:view` / `kb:edit` | USER | 知识库、文档的查看与增删改 |
| `chat:use` | USER | 会话与问答 |
| `user:list` / `user:ban` / `user:assign-role` | ADMIN | 用户列表、封禁解封、调整角色 |
| `role:view` / `role:assign-menu` | ADMIN | 角色列表、保存角色菜单 |
| `menu:view` / `menu:edit` | ADMIN | 菜单列表与编辑 |
| `audit:view` | ADMIN | 审计日志查询 |

用户管理接口按用户 ID 操作账号字段，不提供按用户 ID 拉取其知识库或聊天记录的接口。

调整角色时：不能把系统中最后一个启用的管理员改成用户或封禁，避免锁死在系统外。内置角色不可删除。

## 5. 阶段

### 阶段 A：上线前安全基线

完成前不对外放账号。

1. **配置外置。** 数据库密码、JWT 密钥、模型 API Key、Redis 密码、初始管理员密码只从环境变量读取。仓库里的 yml 只留占位符。生产 JWT 密钥至少 32 字节随机串。已暴露的模型 Key 在智谱控制台作废。
2. **CORS 白名单。** 只放行网页域名和 App 调试来源。上线配置不再使用 `*`。
3. **关闭首版不需要的入口。** 生产环境关闭 Knife4j。MCP 端点默认拒绝，不能因为 Token 为空就放行。
4. **账号状态生效。** 登录、刷新、已登录请求都要求 status = 1。封禁立即生效。
5. **退出登录。** 新增 `POST /user/logout`。退出后旧 Refresh Token 不能再换 Access Token。Access Token 仍靠 2 小时有效期。
6. **注册校验。** 用户名 4–32 位，字母、数字、下划线。密码至少 8 位，并包含字母和数字。登录失败返回「用户名或密码错误」。
7. **上传约束保持在服务端。** 扩展名白名单、20MB。文件名不参与磁盘路径拼接。

### 阶段 B：角色、菜单、权限（同一库）

1. 建 `role`、`menu`、`role_menu`，`user` 增加 `role_id`，写初始数据和第一个管理员。
2. 登录信息带角色。`GET /menu/nav` 按角色和 `client` 返回树。
3. 实现 `@RequirePermission`，给现有知识库、文档、问答接口补上用户权限码。
4. 管理接口：用户列表与封禁、角色列表、角色保存菜单、菜单维护、审计日志列表。这些接口只接受管理员权限码。
5. 注册忽略任何角色字段，固定 `USER`。

本阶段用接口验收，先不改页面：用户 Token 调用管理接口得到 403；管理员 Token 调用后能改角色；改完后原用户再取 `/menu/nav` 结果变化；管理员 Token 调用知识库列表只返回自己创建的库。

### 阶段 C：网页改为动态路由

1. 静态路由只留登录、注册、布局、403、404。
2. 登录后拉取菜单并 `addRoute`，侧栏改为渲染接口树。
3. 组件白名单包含：知识库列表、知识库文档、智能问答、用户管理、角色管理、菜单管理、审计日志。
4. 普通用户登录后只看到知识库和智能问答，地址栏输入 `/user` 等管理路径进入 403。
5. 管理员登录后只看到管理菜单，地址栏输入 `/kb` 进入 403。
6. 用户管理页可以封禁、解封、改角色。角色页可以勾选菜单。菜单页可以改名称、排序、是否可见、所属端。
7. Token 刷新失败时清除本地登录态和已注册的动态路由，回到登录页。

### 阶段 D：App 最小闭环（`ai-app`）

技术选型固定为现有 uni-app Vue 3 工程，用 HBuilderX 跑 Android。

页面：登录 / 注册、首页（按 `/menu/nav?client=app` 生成入口）、知识库、文档、问答、我的。

普通用户走完与网页相同的问答路径。管理员登录后不出现管理入口。接口、上传字段、SSE 事件与网页一致。

App 侧约束：

- 问答使用 `uni.request` 的 `enableChunked` 拼接 SSE。分块不可用时，同一接口改为收完再展示，不改后端协议。
- 上传使用 `uni.uploadFile`。
- Token 放 `uni.setStorageSync`。退出时先调 logout，再清空本地存储。
- 接口根地址单独配置。开发可用局域网 HTTP，上线使用 HTTPS。
- 删掉模板里的相机、电话、读日志、改系统设置权限。
- `pages.json` 声明上述页面。菜单仍以后端结果为准。

### 阶段 E：首版之后

1. 文档失败重试、向量索引从 MySQL 切片重建。
2. 低相关度时明确回复「资料不足」。
3. 引用打开原文切片。
4. 把提示词、回答风格配进菜单（组件键已在白名单时，只需数据，不再改路由表）。
5. 知识库成员，以及用户级 MCP Token。
6. 一个用户多个角色时，再把 `user.role_id` 拆成用户-角色关联表。
7. 按钮级权限、App 管理页、iOS 打包。

## 6. 首版接口

| 用途 | 方法与路径 | 谁可以调用 |
| --- | --- | --- |
| 注册 | `POST /user/register` | 匿名。角色固定为用户 |
| 登录 / 刷新 / 退出 / 当前用户 | 现有用户接口，退出为新增 | 退出和当前用户需登录 |
| 当前用户菜单 | `GET /menu/nav?client=web\|app` | 已登录 |
| 知识库、文档、会话与问答 | 现有路径 | 用户角色，且只能操作自己的数据 |
| 用户列表、封禁、改角色 | 阶段 B 新增 | 管理员 |
| 角色列表、保存角色菜单 | 阶段 B 新增 | 管理员 |
| 菜单列表与编辑 | 阶段 B 新增 | 管理员 |
| 审计日志 | 现有查询接口收口到 `audit:view` | 管理员 |

已有接口的字段保持兼容。用户信息只增加角色相关字段。App 和网页都消费 `/menu/nav`，不各自写一套菜单。

## 7. 上线检查

同时满足才算最小上线：

- 网页普通用户与 Android App 普通用户都能走完第 1 节的问答路径。
- 网页管理员能管用户、角色、菜单和审计日志，不能打开别人的知识库内容。
- 公开注册得到的账号角色是用户。请求里自带的角色字段无效。
- 用户 Token 访问管理接口为 403。管理员 Token 访问用户知识库写接口时，只能动自己的库。
- 侧栏和业务路由来自 `/menu/nav`。前端源码里没有「按角色 if/else 列出知识库、问答、用户管理」这种菜单表。
- 直接输入未授权地址进入 403，对应接口也是 403。
- 用户 A 不能读、改、删用户 B 的知识库、文档、会话和消息。
- 封禁立即不能登录、刷新、调用业务接口。最后一个管理员不能被取消或封禁。
- 退出登录后 Refresh Token 失效。
- 生产密钥来自环境变量。生产环境打不开 Knife4j，MCP 不能被空 Token 调用。CORS 不是全开放。
- App 安装包不含相机、电话、读日志权限。

## 8. 假设

- 首版部署在你自己的服务器，HTTPS 由反向代理终止，库仍是现在的 `ai_java`。
- 管理功能只在网页完成。App 是普通用户客户端。
- 对象存储、知识库共享、应用商店上架不在这一轮。
- 模型调用仍走智谱云端。试用说明里写明文档会发送到云端模型做向量化和回答。

## 9. 后续参考：智能体语言选型

本节不改变第 1–8 节的首版范围，也不作为当前开发任务。记录 2026-10-10 的结论，避免以后把问答服务改写成 Python。

智能体主链路继续放在现有 Java 服务（`ai-agent`，Spring AI）里。账号、角色、菜单、知识库归属和 App 接口都在这一侧。文档摄取在 `DocumentIngestWorker` 中切分后调用 `vectorStore.add()`，由 `EmbeddingModel` 请求智谱 `embedding-3`，向量写入 Redis。相似度检索在 Redis 完成。应用代码负责切分、调用接口、按知识库过滤和拼提示词，向量计算在云端模型，不在本机做矩阵运算。

Python 更适合本机加载 Embedding 或重排序模型、微调、批量评测和离线实验。那些场景出现之前，不把摄取和问答拆到 Python 进程。拆开会让每次上传和提问再传递一次身份，用户数据隔离多一条边界。

若以后要在自己的机器上跑向量模型或重排序，再增加一个单独的 Python 计算进程，由 Java 在摄取或检索时调用。用户、动态路由、问答接口和 App 仍留在现有服务。
